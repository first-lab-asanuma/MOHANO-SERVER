매칭 후보 노출·응답 가능성 기준
===============================

목적
----
통화 신청을 수락할 가능성이 있는 사용자만 후보로 노출한다. 단순히 가입·온보딩을 마친
사용자를 모두 보여 주면, 응답하지 않는 신청과 5초 대기 실패가 과도하게 늘어난다.

현재 후보 자격
--------------
후보는 아래 조건을 모두 만족해야 한다.

1. 본인이 아니어야 한다.
2. 계정 상태가 `active` 또는 로컬 개발용 `seed`여야 한다.
3. 온보딩 프로필이 완료되어야 한다.
4. 요청자의 1인칭 조건인 국가·성별·연령 범위에 맞아야 한다.
5. 아래 둘 중 하나로 통화 수신 가능 상태여야 한다.

   - 최근 90초 안에 foreground heartbeat를 보낸 온라인 사용자
   - `call_notifications_enabled=true`이고 비어 있지 않은 push token이 등록된 사용자

연령 비표시 사용자의 실제 연령은 4번 필터에만 쓴다. 공개 후보 응답의 `age`는 null로
반환하므로 카드에는 표시하지 않는다.

통화 신청 시 재검사
-------------------
후보 목록을 받은 시점과 통화 신청 시점 사이에는 상태가 바뀔 수 있다. 따라서
`POST /v1/call-requests`는 대상의 계정·프로필·수신 가능 상태를 다시 검사한다. 실패하면
`409 candidate_unavailable`을 반환하며 앱은 다음 후보로 이동할 수 있다.

데이터와 API
------------
- `users.last_active_at`: 마지막 foreground heartbeat의 UTC 시각
- `users.call_notifications_enabled`: 통화 알림 수신 동의
- `users.push_token`: FCM/APNs 전달에 사용할 현재 기기 token. 공개 API나 로그에 넣지 않는다.
- `POST /v1/me/availability/heartbeat`: 앱이 foreground인 동안 45초마다 호출한다.
- `GET /v1/me/availability`: 온라인 여부, 알림 동의, token 등록 여부를 조회한다.
- `PUT /v1/me/availability`: 알림 동의와 token을 등록·갱신·폐기한다.

Flutter 동작
-----------
- 로그인 복원, 로그인 완료, 온보딩 완료 후 home 상태가 되면 즉시 heartbeat를 보낸다.
- foreground 상태에서는 45초마다 heartbeat를 반복한다.
- background, inactive, detached 상태에서는 반복을 멈춘다.
- 서버는 90초가 지나면 온라인 상태를 자동 만료로 간주한다. 별도의 offline 요청은 보내지 않는다.

로컬 개발
---------
- `seed` 후보에는 개발 중 매칭이 비지 않도록 알림 동의와 로컬 전용 token을 부여한다.
- 실제 사용자에게는 Firebase token이 등록되기 전까지 온라인 heartbeat만 후보 노출 근거가 된다.

후속 구현
---------
- Firebase Cloud Messaging(Android) 및 APNs(iOS) 초기화, OS 권한 요청, token 등록·회전·폐기
- token을 기기별로 분리한 `notification_devices` 테이블 전환. 현재는 MVP 단일 token 구조다.
- 실제 통화 신청 push 발송, 실패 token 자동 폐기, 재시도·rate limit, 전송 결과 관측
- 수신자 앱의 통화 신청 inbox 갱신과 push를 통한 수락 화면 진입
- 사용자별 통화 수신 가능 시간대·방해 금지 시간·하루 수신 횟수 제한
- 차단·신고·탈퇴·운영 제한 상태를 후보 SQL과 통화 신청 재검사에 반영
- 최근 통화·거절·무응답 이력 기반의 재노출 간격과 품질 점수
- 온라인/알림 가능 여부를 공개 프로필에 표시할지 여부와 개인정보 정책 검토
- heartbeat 남용 방지, 서버 시간 기준, 다중 기기와 동시 세션의 정확한 presence 집계
